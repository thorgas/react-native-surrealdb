# Native-values profile precision review

Status: **design review only**. This note proposes exact rules for two gaps in
the engine's draft at
`df88ce632bf8784b8bed439a19da224ef9936583:spec/wire-native-values-profile-draft.md`.
It does not implement or prove native-values sync, change the SDK ABI, or
authorize changes to `surrealdb-sync/1`.

The source comparison used the pinned engine authority crate
(`surrealdb = "=3.2.4"`) and its `Cargo.lock`. That lock resolves
`rust_decimal` **1.42.1**, not 1.43.0. The draft's existing Decimal source
reference to 1.43.0 should be corrected before it is treated as pinned-source
evidence.

## Recommended fingerprint rule

Keep v1 byte-for-byte unchanged. Its current implementation in
`crates/surrealdb-sync-protocol/src/canonical.rs` hashes deterministic CBOR for
the six-item array

```text
[
  "surrealdb-sync/1/commit-fingerprint/sha256",
  "surrealdb-sync/1",
  partition_id,
  client_id,
  client_commit_id,
  ordered_operations
]
```

and formats the digest as `sha256:` followed by 64 lowercase hex digits. The
native-values profile should use exactly the same framing and identity fields,
but replace both profile strings and encode operations using only the native
profile's canonical types:

```text
[
  "surrealdb-sync/native-values/1/commit-fingerprint/sha256",
  "surrealdb-sync/native-values/1",
  partition_id,
  client_id,
  client_commit_id,
  ordered_native_operations
]
```

Encode that whole array once as deterministic CBOR, then SHA-256 those bytes.
Do not hash concatenated fields, JSON bridge bytes, an HTTP envelope, or just
the operation payload. The array provides field boundaries; the domain and
profile strings deliberately both bind the digest to this family, following
the v1 pattern. Preserve operation order. A profile-specific verifier must
reject a v1 fingerprint where a native-values fingerprint is expected and
vice versa; there is no fallback or cross-profile retry.

Recommended native-values structural identity representation for operation
vectors, pending wire-schema review:

```text
RecordIdentity := [table_text, RecordKey]
RecordKey      := [0, signed_i64] | [1, string] | [2, 16_uuid_bytes]
Delete         := [1, RecordIdentity, base_version_u64]
```

This is a candidate for the operation identity field, not a decision about
semantic CBOR tags for values. It keeps integer key `7` distinct from string
key `"7"`. The draft still needs its complete operation/envelope and typed
value encodings frozen before a full-value fingerprint can become a golden.

## Recommended Set representative and ordering rules

The pinned SurrealDB `surrealdb-types` 3.2.4 source defines `Set` as a
`BTreeSet<Value>` and `From<Vec<Value>>` collects the vector into that set
(`src/value/set.rs:11-33`). `Value::Ord` delegates numbers to `Number::Ord`
(`src/value/mod.rs:132-150`). The number comparison treats `-0.0` and `+0.0`
as equal and compares integer/float/decimal variants numerically
(`src/value/number.rs:147-198`); `Number::PartialEq` delegates cross-variant
equality to that comparison (`:318-337`). The locked `rust_decimal` 1.42.1
implements Decimal equality through `Ord` (`src/decimal.rs:2750-2778`) and its
comparison rescales coefficients when scales differ
(`src/ops/cmp.rs:45-70`).

Therefore the first equal value inserted into `Set::from(Vec<Value>)` is the
surviving representative: the set does not retain both or normalize the
representative. Recommended canonical-wire behavior:

1. Encode the exact values already present in the native Set. Never normalize
   a Decimal, convert a number through text or float, or canonicalize signed
   zero before encoding. The surviving representative's variant, bits, and
   Decimal coefficient/scale are part of the wire representation and native
   fingerprint.
2. Encode each member independently using the complete native-values canonical
   value encoder. Sort those encoded byte strings by unsigned lexicographic
   byte order (first differing byte; shorter prefix first). This is the wire
   order; do not use `Value::Ord`, `Hash`, locale ordering, or source insertion
   order as a cross-platform wire-order rule.
3. A decoder requires strict ascending encoded-member bytes, then constructs
   native Set membership and rejects if the resulting cardinality differs
   from the encoded list. Thus duplicate bytes and distinct encodings that
   compare equal natively are both rejected; decoding never silently chooses
   a new representative.
4. Count and validate the whole Set before allocating its sorted output.

Recommended constructor vectors (the expected member is preserved with its
original representation):

| Input order | Expected native Set member |
| --- | --- |
| `Int(1), Float(1.0)` | `Int(1)` |
| `Float(1.0), Int(1)` | `Float(1.0)` |
| `Decimal(1.00), Int(1)` | the original `Decimal(1.00)` |
| `Int(1), Decimal(1.00)` | `Int(1)` |
| `Float(-0.0), Float(+0.0)` | the original `Float(-0.0)` |
| `Float(+0.0), Float(-0.0)` | the original `Float(+0.0)` |

For a canonical Set payload, test ordering with at least two unequal
representatives whose native `Value::Ord` order differs from their encoded
byte order. Also submit `Int(1)` and `Float(1.0)` together in an encoded Set;
the decoder must fail because native construction yields one member instead
of two.

The existing draft says to preserve the actual surviving member. Making that
normative means two SurrealDB Sets that compare equal under native `Eq` can
have different native-values bytes and fingerprints if they retained
different representatives. This is the lossless choice and avoids mutating
existing native values, but it is not equality-class canonicalization. The
protocol review must explicitly accept this consequence or instead choose a
normalization rule that changes the draft's preserve-type/scale requirement.

## Unresolved decisions and evidence boundary

- Confirm the proposed fingerprint domain string and 6-item envelope; then
  assign the complete native operation/value tags and capture non-empty
  Datetime, Decimal, UUID, Set, typed-ID and full-note vectors in the actual
  Rust and SDK implementations.
- Confirm that typed RecordKey discriminants `[0, 1, 2]` and their payload
  shapes are acceptable, or assign the wire-schema's fixed semantic tags.
- Explicitly choose representative-preserving fingerprints (recommended) or
  equality-class normalization for native-equal Sets. No implementation may
  silently pick one.
- Add cross-language goldens for input insertion-order permutations, bytewise
  Set order, duplicate native equality, scalar Decimal scale, signed zero,
  and exact preimage bytes. Hand-derived vectors above are not a substitute.

Source comparison is not runtime proof. The pinned dependency source establishes
the BTreeSet and numeric comparison rules; this SDK branch does not contain a
native-values encoder, server route, persisted profile binding, or full Note
sync. SDK `.3` artifact success does not close the persisted Note sync gate.
